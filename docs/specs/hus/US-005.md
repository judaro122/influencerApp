# US-005: Upload Video via API

## As an authenticated user, I want to upload a video file via API so it can be processed.

## Given / When / Then

- **Given** an authenticated user with at least one linked YouTube channel.
- **When** the user sends a POST request to `/api/videos/upload` with a multipart video file and a `channelId`.
- **Then** the video file is streamed to object storage, persisted as a `Video` aggregate in `RECEIVED` status, and a `videoId` is returned (HTTP 201).

## Acceptance Criteria

1. POST `/api/videos/upload` accepts `multipart/form-data` with `file` and `channelId`.
2. The `Idempotency-Key` header is required; duplicate keys within 24h return the cached response (same `videoId`).
3. The `file` is validated: `Content-Type` must match `video/*`, `Content-Length` must not exceed 100MB, filename must not contain path traversal characters.
4. The video file is streamed to MinIO (or local fallback if `storage.type=local`) using multipart upload with chunked transfer; never fully buffered in memory.
5. A `VideoEntity` row is created with `status = RECEIVED`.
6. The response includes `{ videoId }` (HTTP 201).
7. Returns `401` (RFC 7807) when no valid JWT is provided.
8. Returns `413` (RFC 7807) when file size exceeds 100MB.
9. Returns `422` (RFC 7807) when file type is not `video/*`.
10. Returns `503` (RFC 7807) when MinIO is unreachable in production.
11. Cross-tenant access is denied: the `channelId` must belong to the requesting tenant.
12. After storage, a `video-received` Kafka event is emitted (kafka-events.md §3).

## Out of Scope

- Video transcoding (v1.0, out of scope per constitution §11.1).
- Thumbnail generation (v1.0, out of scope per constitution §11.2).
